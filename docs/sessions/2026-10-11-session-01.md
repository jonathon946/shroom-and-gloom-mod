# Session 01 — 2026-10-11 — project set up, sibling mods and Prism surveyed, game inspected on disk

Scope, from the maintainer's request: set up the project to the tree's standards; inspect the other mod projects and the mods installed on this machine; check the Dwarf Fortress mod's Prism adoption so Prism is used here from the start; begin inspecting Shroom and Gloom.

## What we did

- Read the shared contract, the working requirements, the templates guide, the field guide and the environment notes.
- Surveyed the three sibling mod projects (Dwarf Fortress, Caves of Qud, Class of '09) for layout, house style and transferable lessons, and scaffolded this project to match the newest form (Dwarf Fortress: instructions adopted by reference, decision log in the plan, open-questions file, no TODO file).
- Surveyed the accessibility mods installed on this machine. Only two other installed games are Unity IL2CPP (Yu-Gi-Oh! Master Duel and No, I'm not a Human), both on MelonLoader 0.7.x. Four installed C# mods call Prism directly.
- Traced Prism in the Dwarf Fortress mod: introduced in its Session 18 (2026-10-10), v0.18.3, through a C shim because DFHack's Lua has no FFI. Correction to the request's premise: Tolk was planned there but never shipped, so Prism replaced the plan, and NVDA still goes through NV Access's own client there because Prism's NVDA backend cannot report "still speaking".
- Inspected the game on disk without launching or changing it. Details in [the reconnaissance record](../recon-2026-10-11.md).
- Wrote `tools/Dump-MetadataNames.ps1` and ran it.
- Created the repository and the hub entry.

## Confirmed by ear / verified by data / unverified

- **Confirmed by ear:** nothing; there is no product yet.
- **Verified by data:** engine and build facts; the class and file names; the loader, speech and Prism details of the installed mods (from their files, logs and decompiled declarations); the Prism header and the Dwarf Fortress binding.
- **Unverified:** whether any loader starts under Unity 2022.3.62f3 IL2CPP; whether the keyboard drives the game's focus system; how exploration plays; that MelonLoader issue 1063 was ever fixed (the issue page names no fix). Web findings were read from search summaries and two fetched issue pages, not from release notes.

## Agile retro

- **What went well:** the metadata gave the game's real architecture in minutes with no extra tools. The sibling survey surfaced the Unity 2022.3.62 loader warning in the Class of '09 notes before any time was spent on code.
- **What did not go well:** the request's premise about Prism replacing Tolk in the Dwarf Fortress mod was slightly off and needed correcting. The field guide's catalog turned out to be stale for five installed games.
- **Product accessibility:** none yet; the game is unplayable without sight today.
- **Session accessibility:** all work was in text and files; no GUI-only step. The documents use headings and lists, no tables. No command was handed to the maintainer, so no paste-commands file was needed.

## Risk analysis

- **No loader starts under this Unity build.** Likelihood medium, impact high. Mitigation: Spike 1 first, three loader options in order, crash logs kept.
- **Game updates break hooks.** Likelihood high, impact medium. Mitigation: build check at session start; per-hook isolation.
- **The focus system is gamepad-only or incomplete.** Likelihood medium, impact medium. Mitigation: Spike 2 measures coverage before feature work.
- **Prism latency.** Likelihood low, impact medium. Mitigation: listen for it in the first ear test; one speech layer to change.

## WCAG 2.2 AA (spirit) audit — surfaces changed this session

No product surface changed. Documentation self-audit: one H1 per file, ordered headings, descriptive link text, no tables, no images, absolute dates, status header on every document.

# Part 3 — loader installed; Spikes 1 and 2; the tutorial opening played through (same session, continued)

## What happened

- The maintainer ran `paste-commands.ps1`; MelonLoader 0.7.3 was installed, and confirmed by ear that the standalone Prism line had been heard.
- **Spike 1 passed.** First start generated the interop assemblies; the mod loaded; Prism reported backend NVDA; the greeting was sent at the title screen.
- **Spike 2 passed, with a detour.** The focus service is off in keyboard mode. Forcing gamepad mode wakes it. Keyboard keys had no effect on it, so the mod now answers the game's action queries itself.
- A mistake: early tests sent keystrokes at the desktop while the maintainer was in another window. They did not reach the game and may have reached that window. Replaced with in-game injection; desktop keystrokes are now a recorded dead end.
- Desktop screenshots were black, so the mod gained a dev bridge that saves the game's own frame, dumps UI text and state, and simulates presses. With it Claude can see and drive the game with the window unfocused.
- The tutorial stalled at the first object for a long time. Cause found by dumping triggers and objects: the shovel can only be focused after the camera has looked at it. `WorldAssist` now marks such objects as seen when in range.
- Played the opening through in tests: shovel, Rusty Shovel card, dig site, Key card, door, next area. Pause menu reached and navigable.
- Spoken descriptions written for cards, world objects, doors, buttons and title paths.

## Confirmed by ear / verified by data / unverified

- **Confirmed by ear:** the standalone Prism line (maintainer).
- **Verified by data:** everything listed under "What works" in STATE, from the mod log, state dumps and in-game screenshots.
- **Unverified:** in-game speech as heard; the real keyboard path; other screen readers; whether cheat keys are live.

## Agile retro

- **What went well:** the killer assumption (a loader) was settled in one start. The game's own pad navigation turned out to cover targeting and menus, which removes most of the planned work on a custom cursor. The dev bridge made a blind, unfocused test loop possible.
- **What did not go well:** keystrokes sent at the desktop (a real intrusion on the maintainer's other work). About an hour lost at the shovel guessing at input paths before dumping the scene's triggers, which showed the cause in one step. Several shell quoting failures.
- **Product accessibility:** the opening minutes are operable by keyboard and described in speech, in tests. Nothing after the tutorial door, no combat, no status queries, no help. Arrival in a new place, doors opening and the first "Press Space Bar" screen are silent. WCAG-spirit gaps: status changes are not announced (4.1.3), no help or key list in-game (3.3.5).
- **Session accessibility:** the one manual step was a single command with a clear end line. The ear test is a lettered checklist in `paste-commands.ps1`. Progress notes in chat were plain text.

## Risk analysis (additions)

- **Real keys behave differently from injected actions.** Likelihood medium, impact high for the first ear test only. Mitigation: it is step B of the checklist; the log shows every hook and action.
- **Forcing gamepad mode breaks something the keyboard mode did** (text entry, mouse users sharing the machine). Likelihood medium, impact low to medium. Mitigation: a toggle key later; `InputBridge.Enabled` already exists.
- **Cheat keys are live and a player triggers one by accident.** Likelihood low to medium, impact medium (a spoiled run). Mitigation: find out; if live, block them.
- **The dev flag ships by mistake.** Likelihood low, impact low (extra logging, a command file being read). Mitigation: packaging step must exclude `UserData`.
- **Save data is no longer fresh.** Certain; impact low because a backup exists. Mitigation: the reset item in STATE.

# Part 6 — walking and speech (same session, continued)

## What happened

- The maintainer asked to think the walking problem through before testing: holding W must stay, announcements must be live so the player can decide to stop or pass by, a toggle would spoil the feel, and a sound alone does not say what the thing is.
- Options weighed: a walk toggle; hiding key repeats from the screen reader with a keyboard hook; an NVDA add-on; NVDA's own interrupt setting; a second voice outside the screen reader's control.
- Chosen with the maintainer: the second voice plus a sound, with the voice's rate following the screen reader's where possible.
- Built: direct voice in `Speaker`, `Cue` for the sound, `Settings` for rate and cue volume, Ctrl+Page Up / Page Down to adjust.

## Confirmed by ear / verified by data / unverified

- **Confirmed by ear:** nothing new.
- **Verified by data:** both backends initialise and accept speech together (standalone test and in the game); arrival lines are sent to the direct voice while the walk input is held; the sound objects build without error; the rate setting is read from NVDA's file (0.66) and saved.
- **Unverified:** how the second voice sounds, whether 0.66 is anywhere near the maintainer's Eloquence speed, whether the sound is audible and pleasant, whether the two voices talk over each other.

## Agile retro

- **What went well:** pausing to design before testing avoided a third listen of something already known to be wrong.
- **What did not go well:** the previous part shipped "hold until release" without flagging clearly enough that it could not meet the live requirement.
- **Product accessibility:** arrival is now a live status message with a non-speech cue and a spoken name.
- **Session accessibility:** discussion only; nothing for the maintainer to run.

## Risk analysis (additions)

- **Two voices overlap or confuse.** Likelihood medium, impact medium. Mitigation: the direct voice is used only while a walk key is held; listen in the third test.
- **Rate mismatch annoys.** Likelihood high on first use, impact low. Mitigation: two keys to adjust, saved.

## WCAG 2.2 AA (spirit) audit — surfaces changed in part 6
